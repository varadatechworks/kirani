# Kirani Phase 1 — PostgreSQL Database Design

**Version:** 1.0 | **Status:** Logical/physical design baseline; implementation migrations must be reviewed

## 1. Design principles
- PostgreSQL is the system of record. Use UUID primary keys and separate human-readable business codes.
- Normalize operational writes; add read models/materialized views only for proven reporting needs.
- Store money as BIGINT minor units (paise) plus ISO currency code. Store quantities as NUMERIC(18,3) or finer precision with explicit unit and, where relevant, measurement basis/moisture.
- Store timestamps as TIMESTAMPTZ in UTC; retain business timezone on cycle/service-area configuration.
- Use CHECK, UNIQUE, FK and exclusion/partial indexes for invariants; validate again in domain services.
- Never use floating point for money or measured mass.
- Immutable ledgers/events: inventory movements, trace events, payment events, loyalty ledger, audit events, processing stage events. Correct by linked compensating records.
- Prefer soft deactivation for master data; never cascade-delete financial, order, batch or audit history.
- Keep PII/private documents separate from public traceability projections.
- Every business table includes created_at, created_by where meaningful; mutable tables also updated_at, updated_by and row_version.

## 2. Naming and common conventions
- Tables/columns: snake_case, plural table names, *_id foreign keys.
- Primary keys: UUID generated by gen_random_uuid().
- Business codes: unique, immutable human-facing identifiers (e.g. PO-2026-000123, SRC-...).
- Status values: constrained text or PostgreSQL enum only when lifecycle is stable; versioned reference/config tables for admin-managed states.
- Money: amount_minor BIGINT, currency CHAR(3); unit price and totals are separate snapshots.
- Quantity: quantity NUMERIC(18,3), unit_code VARCHAR(16); conversion requires explicit unit conversion record.
- JSONB: only for provider payload snapshots, flexible evidence/metadata, or versioned configuration—not as substitute for relational core data.
- Actor fields reference users where possible; system actor is explicit.

## 4. Critical relationship and integrity rules
1. Customer → recurring_baskets → recurring_basket_versions → items; one_time_baskets are unique per customer/cycle.
2. Monthly order has one immutable order snapshot and many order items. Each order item records basket type and source version.
3. A goods receipt creates one or more source batches. Each source batch retains supplier/farmer identity and receipt reference.
4. Processing jobs consume only explicitly assigned inventory/source batches. Stage outputs create new inventory batches; genealogy edges link all parent inputs to all children.
5. Genealogy supports many-to-many for approved blends, but default workflow creates one source-specific job. Enforce no self-edge and prevent cycles in service/DB validation.
6. Package source allocations point to actual inventory batches and source genealogy; sum of allocations must equal package net quantity within configured tolerance.
7. Inventory balance changes only through inventory movement events. Use transaction/locking to prevent negative saleable stock.
8. Package public token is random, high entropy and stored as hash; public endpoint resolves curated projection.
9. Payment provider event ID is unique per provider; idempotency keys unique in operation scope.
10. Loyalty redemption allocation sums to redemption points/value; each lot cannot be over-consumed.
11. Status transition events are append-only; current status is projection updated transactionally.
12. Foreign keys on historical business data use RESTRICT/soft deletion, not cascading deletes.

## 5. Required constraints and indexes
- UNIQUE users.mobile_e164; UNIQUE products.sku; UNIQUE monthly_cycles.cycle_code; UNIQUE orders.order_code; UNIQUE package_units.package_code and public_token_hash.
- UNIQUE recurring_basket_versions(recurring_basket_id, version_no).
- UNIQUE one_time_baskets(customer_id, cycle_id).
- UNIQUE payment_events(provider, provider_event_id); UNIQUE scoped idempotency key for payment/refund actions.
- UNIQUE processing_job_stages(job_id, sequence_no); UNIQUE listing_approvals(listing_id, version) where decision finality rules allow.
- Index all FK columns used in joins and deletes/updates.
- Composite indexes: monthly_orders(cycle_id,status); monthly_orders(customer_id,created_at DESC); order_items(product_id,cycle_id); farmer_listings(status,availability_start,availability_end); inventory_batches(product_id,location_id,condition); inventory_movements(batch_id,occurred_at); processing_jobs(facility_id,status,assigned_at); traceability_events(entity_type,entity_id,occurred_at); delivery_assignments(operator_id,status,window_id); payment_transactions(order_id,status); loyalty_earning_lots(wallet_id,expires_at).
- Partial index saleable inventory where condition='SALEABLE' and qty_on_hand > 0; open tickets where status not terminal; pending outbox where published_at IS NULL.
- Use PostGIS only if precise geo queries/route features justify dependency; otherwise store latitude/longitude with access controls and spatial indexes only when needed.

## 6. Transaction boundaries
- Basket confirmation: lock cycle/customer basket version; verify cutoff and active customer; compute server-side price/tax; persist order, lines, immutable snapshot and outbox event atomically.
- Procurement receipt: persist receipt, source batch, inspection and inventory movement atomically; accepted/rejected quantities reconcile to received quantity.
- Processing stage completion: lock consumed batches; validate available quantity; persist stage event, output batches, genealogy, movements, reconciliation and audit atomically.
- Packing: lock inventory; allocate source batches; create package, package-source allocation, label and stock movement atomically.
- Payment webhook: verify signature before state transition; unique provider event; idempotently apply transaction and outbox event.
- Loyalty redemption: lock wallet/lots; allocate exact lot quantities; enforce balance and conversion; write ledger/redemption atomically.
- COD reconciliation: lock collection and assignment; prevent duplicate reconciliation.

## 7. Data retention and privacy
- Keep financial, order, tax, procurement, traceability and audit records for legally required periods; retention schedule requires legal/accounting advice.
- Restrict personal data, bank details, identity documents and exact farm/customer coordinates by role.
- Public QR view is a dedicated projection with field allowlist and source disclosure/consent policy.
- Deletion requests follow applicable law and retention exceptions; anonymize where permitted rather than deleting records needed for legal traceability.
- Backups are encrypted and access-controlled; test restoration and retention expiry.

## 8. Migration strategy
- Use numbered, immutable migration files with checksum and migration history table.
- Create extensions only when justified; enable UUID generation in PostgreSQL.
- Deploy additive schema first; backfill in batches; dual-read/write only with explicit migration plan; remove obsolete columns only after application cutover.
- Seed reference data idempotently (roles, permissions, units, statuses, initial stage templates).
- Production migrations must be backward-compatible with currently deployed app version; destructive migrations require backup, maintenance plan and rollback/forward-fix strategy.
- Test clean install, upgrade from previous version, representative data migration and rollback/restore in CI/staging.

## 9. Implementation note
This is a logical schema catalogue, not executable DDL. Before coding, engineering must convert each entity into reviewed SQL migrations with exact nullability, FK actions, checks, enum/reference strategy, precision, indexes, row-level access strategy and retention rules. Never infer omitted columns as production-ready defaults.
